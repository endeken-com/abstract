# ABS-184: what the main thread does when you navigate

Measured on ABS-159's synthetic profile (50 projects, 1,000 chats, 143 marked
working), plus six long chats of 6,000 log lines each and ten chats streaming
about 25 lines a second. Release builds, demo mode:

```
ABSTRACT_DEMO_NAV=15 Abstract.app/Contents/MacOS/Abstract --demo
```

`NavigationProbe` (Abstract/Demo) adds the profile, then switches chats and
tabs, opens Automations and New Chat, and sends a message, several times each.
For each action it reports how long until the run loop that built the new
screen's views went back to waiting, and the main thread's processor time in
that span. `HangMonitor` (Abstract/App/Perf.swift) logs every stretch over
100 ms with the signposted work in it; it runs in debug builds and in any build
started with `ABSTRACT_HANG_MONITOR=1`. Main-thread attribution comes from
`sample` while the probe switches chats in a loop.

The Mac these ran on was shared with other agents' builds (load average 25 to
150), so wall times are noisy; each number is a median of 4 to 6 runs, and the
attribution is from sample counts, which noise skews far less. A demo window
that isn't in front gets App Nap and draws nothing, so only runs whose window
drew are compared below.

## Before: the top main-thread costs

Per warm chat switch (Release, `sample` over 21 switches):

| Cost | Per switch | Where |
|---|---|---|
| Session locks on every `destination` change: open/flock, own-pid `sysctl`, atomic JSON write with fsync, a scan of the whole locks folder reading each holder | ~225 ms (45% of the main thread) | `syncLocks()`, `SessionLock.publish`, `refreshCLIDriven()` |
| Rebuilding the whole main menu, because the menu commands read `sessions` and the chat showing | ~100 ms (20%) | `AbstractCommands.body`, `AppKitMainMenuItem.updateMainMenu` |
| Transcript rows rebuilt (35 rows: Markdown, layout) | most of the rest | `TranscriptController`, Textual |
| Saving `mainTabs` to SQLite (with fsync) on every tab change | ~15 ms | `mainTabs.didSet` |
| Reading the chat's log for `abstract` on every navigation | ~8 ms | `followCLIChat()` |

In a Debug build, 70% of a transcript layout pass was Textual rescanning every
attributed run for attachments on each size change, even in prose without any
(`TextBuilder.sizeChanged`).

First opening of a 6,000-line chat: `loadTimelineIfNeeded` 550 ms on the main
thread (replay 385 ms, read 99 ms, publish 49 ms).

Sending to a chat whose agent had stopped: `sendFollowUp` 64 ms, of which the
engine counted every line of the log twice (once to log the message, once to
launch the agent).

### The ticket's suspects

- **`reload()` doing synchronous SQLite.** Confirmed costly but not the cause:
  none of the five actions calls it except submitting from New Chat
  (`startChat` → `reloadSessions()`, 61 ms in Debug at 1,000 chats). A full
  `reload()` on this profile is 80 to 420 ms in a Debug test run, against under
  2 ms to save one chat and update its entry
  (`NavigationBench.savingOneChatInsteadOfReloading`).
- **`loadTimelineIfNeeded` reading the whole log on open.** Confirmed: 550 ms
  for the first opening of a long chat.

Also measured, not part of the five actions: background plugin scripts asking
for a snapshot of every chat (about 10% of the main thread with 1,000 chats),
plugin hosts' once-a-second watchdog (`PluginBackgroundRunner.tick`), and
parsing agent output on the main thread (12% with ten chats streaming).

## What changed

- **Locks off the main thread.** The app's lock files are written and removed
  on a serial queue (`abstract`'s stay synchronous); the process start time is
  asked of the kernel once; paths no longer `stat` the disk
  (`appendingPathComponent(_:isDirectory:)`); who drives which chat from the
  command line is read in the background.
- **Menus rebuild only when an item changes**, from `MenuFacts`
  (AppModel+Menus).
- **Settings and panel layouts saved in the background**, in order; quitting
  waits for them. A chat's panel layout is read from the store once, not on
  every redraw.
- **Long chats open on their newest page** (256 KB from the end of the log),
  and the whole log is read and replayed in the background
  (`TimelinePage`).
- **The engine remembers each log's line count** with its size, so a message
  or a launch doesn't count the whole log again.
- **Targeted store updates** (`StoreOrder`) instead of `reload()` when starting,
  deleting or moving chats and projects, saving project settings, automations,
  workflows and setups. `reload()` remains for launch, removing a project
  (which cascades), changes made by `abstract`, and automation runs.
- **Narrower invalidation:** sidebar rows observe their own "showing" mark, and
  the sidebar list no longer depends on the chat showing.
- **Textual** skips the attachment rescan, and the redraw it caused, for text
  without attachments.

## After

Release, window drawing, same probe and profile. Before is the baseline run;
after is the median of two runs (A1, A2).

| Action | Before | After |
|---|---|---|
| Switch chat | 1,088 ms | 354 ms |
| Switch tab | 1,057 ms | 354 ms |
| Open Automations | 460 ms | 129 ms |
| Open New Chat | 535 ms | 157 ms |
| Send a message (composer clears, message shows) | 295 ms | 228 ms |
| First opening of a 6,000-line chat | 1,645 ms | 350 ms |
| Longest main-thread stall in the second after an action | 1,646 ms | 610 ms |

With the window not drawing (so only the model's main-thread work counts),
switching chats went from 220 ms (mostly waiting on lock files) to 3.5 ms, and
opening a long chat from 5.8 s to 0.6 s under the same load.

## Not done: still over 100 ms

What's left is building views: opening a chat builds its transcript's rows
(about 35, each a Textual Markdown view) and its composer from scratch, about
300 ms, and leaving a chat redraws its visible rows once more. Getting under
100 ms needs the transcript kept alive across switches (or rows that cost far
less to build), which is a change to `TranscriptController` and the chat
screen's lifetime, bigger than this ticket. Also left: replaying a long chat's
whole log finishes with one publish of every row on the main thread (up to
about 270 ms under heavy load), and agent output is still parsed on the main
thread.

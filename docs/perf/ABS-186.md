# ABS-186: keeping recently shown transcripts

Same profile and probe as ABS-184 (`docs/perf/ABS-184.md`): ABS-159's synthetic
profile, six 6,000-line chats, ten chats streaming, Release builds, demo mode:

```
ABSTRACT_DEMO_NAV=15 Abstract.app/Contents/MacOS/Abstract --demo
```

Launched beside another running copy of Abstract, the demo's own window never
opened (SwiftUI never set up the `Window` scene in that process), so nothing
drew and every action measured under a millisecond. The probe now opens a
window hosting `RootView` itself when the app has none, and prints whether its
window is visible; every number below comes from runs whose stretches contain
`body.BlockView`. It also prints whether a chat comes back where you were
reading, and the memory the kept transcripts hold.
`ABSTRACT_DEMO_NAV_LOOP=<n>` repeats one action (`ABSTRACT_DEMO_NAV_LOOP_ACTION=automations`
for Automations) for `sample`.

The Mac was shared with other builds (load average 17 to 47), so before and
after ran interleaved, twice each.

## Before: where a switch went

Per warm chat switch, from the probe and `sample`:

- **35 transcript rows built from scratch** (`body.BlockView` ×35): new
  hosting views, measured, then laid out by SwiftUI and Textual.
- **Every layout pass guessed every row's height again**: `estimate` splits
  each reply into lines, for every row of the chat (thousands), several times
  per pass. About 40% of the transcript's layout time.
- **Each update rebuilt the item list** of the whole chat even when nothing
  had changed.
- **The chat's More menu worked out the latest launch** by building every
  block of the timeline on each toolbar redraw.
- **Leaving** a chat for Automations or New Chat re-evaluated its ~11 visible
  rows as their views left the window.

## What changed

- **The last four chats shown keep their transcript** (`KeptTranscripts`,
  `AppModel.transcript(for:)`): the controller with its scroll view, rows,
  heights and reading position. A kept transcript does nothing while out of
  sight (no rebuilds while its agent streams, no measuring ahead) and catches
  up on what changed when it shows. A chat deleted, archived or dropped from
  the four lets go of its transcript.
- **Only the rows on screen are built** when a chat shows; the screen above
  and below follows a quarter of a screen at a time in idle moments. A kept
  transcript holds only the rows around where you were (about 20 views).
- **Row height guesses are kept** per row and width, until the row changes.
- **An update that changes nothing leaves the rows be.**
- **The latest launch is kept with the chat's feed**, worked out once per publish.

## What a kept transcript can't keep

A row's hosting view rebuilds its SwiftUI graph whenever it joins a window
again, even the same window (tried: moving kept transcripts to a hidden view
in the window instead made every row rebuild, on leaving and on coming back;
`.equatable()` rows change nothing). So coming back to a kept chat still
renders the rows on screen (about 14, ~45 ms), and most of the rest of a
switch is SwiftUI building the chat screen itself (`ChatView` is
`.id(sessionId)`): toolbar, composer, panels and the sidebar's update, about
130 ms.

Getting a switch under 100 ms needs the transcript (or the whole chat screen)
to stay in the window across switches: a transcript layer outside the chat
screen's SwiftUI tree, with its own answers for z-order (the find bar and
jump button sit over it), hit testing and the title band's blur. That's a
follow-up.

## After

| Action | Before | After |
|---|---|---|
| Switch chat (recently shown) | 435–464 ms | 176–187 ms |
| Switch tab (recently shown) | 356–586 ms | 175–185 ms |
| Open Automations from a chat | 122–132 ms | 95–99 ms |
| Open New Chat from a chat | 167–226 ms | 135–136 ms |
| First opening of a 6,000-line chat | 340–523 ms | 219–222 ms |
| Send a message | 207–235 ms | 182–193 ms |
| Longest stall in the second after a switch | 509–583 ms | 182–208 ms |

Medians of 4 to 6 actions per run, two runs each. Memory with four
transcripts kept: 19 to 20 row views each, 6 to 28 MB of the process's
footprint across runs (released on letting them go). Coming back to a chat
read halfway up puts it within 3 to 6 points of where it was.

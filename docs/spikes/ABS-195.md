# ABS-195: Google coding agent compatibility probe

Probed 2026-11-09 in the isolated ABS-195 worktree. **Implementation gate remains closed:** no authenticated Antigravity turn or account model catalogue was available. The ABS-90 spike explicitly says, “No-go for building any single one from documentation alone.” A bundled picker entry would claim a verified chat transport that this probe could not exercise.

## Transport and authentication

- Installed `gemini` is **0.66.0**. `gemini -p 'Reply with OK.' --output-format stream-json --model auto` exits **55** before a turn. The cached individual free-tier credential returns `IneligibleTierError`, `reasonCode: UNSUPPORTED_CLIENT`, and directs this account to Antigravity. This reproduces the 0.37.1 blocker from [ABS-90](ABS-90.md). Gemini CLI's current [authentication guide](https://geminicli.com/docs/get-started/authentication/) still documents individual Google sign-in and also API-key or Vertex AI use in headless mode; that documentation does not make this account usable through Gemini CLI.
- Google's [Antigravity CLI](https://antigravity.google/docs/cli/headless/) is the supported replacement candidate. Its [installer](https://antigravity.google/docs/getting-started?tab=cli) provided `agy` **1.5.3**, checked against `agy --help`. It supports `--output-format stream-json`, `--input-format stream-json`, `--conversation <id>`, `--model`, `--effort`, `--mode`, and `agy models`. The [authentication guide](https://antigravity.google/docs/install) documents personal Google accounts, including Free, Pro, and Ultra, and cached credentials for later headless runs. It also documents a separate Gemini API-key path that requires `modelProvider: "gemini"` as well as `GEMINI_API_KEY`.
- This Mac has no authenticated Antigravity session or Gemini API key in the environment. `agy models` exits **1** with “Please sign in to view available models.” A headless `agy -p ... --output-format stream-json` requested browser OAuth; the probe was interrupted without signing into the user's account. It emitted only an `ERROR` result with `authentication failed or timed out`, no agent turn. Account model IDs and the live tool stream therefore remain unverified.

## Verified protocol surface, pending a signed-in probe

The vendor's [headless reference](https://antigravity.google/docs/cli/headless/) documents `init`, `step_update`, and `result` NDJSON records. Tool steps carry `step_index`, `tool_name`, `tool_info.parameters`, `tool_info.output`, and optional `tool_info.error`. Response steps stream `text_delta`. The terminal result carries `conversation_id`, status, error, and token usage. A later process resumes with `--conversation <id>`; a live process can accept user NDJSON lines on stdin, but only text content blocks. This is enough to design an Abstract agent script, yet the actual fields and account access must be captured before shipping.

`agy models` is the account-specific source of model IDs. The IDs in vendor documentation are examples, not a validated catalogue for this account. The installed CLI also accepts `low|medium|high|xhigh|max` for `--effort`, broader than the current headless page's three-level example. Do not pin announcement-derived model IDs.

Headless approval requests are [soft-denied](https://antigravity.google/docs/cli/headless/#permissions-in-headless-mode), with notices on stderr; they cannot be answered through the stream. `--dangerously-skip-permissions` approves all tools. Accordingly the plugin must not advertise live `permission` or `permission.mode`. [Antigravity customization discovery](https://antigravity.google/docs/customization-discovery?tab=cli) documents workspace `.agents/skills/` and `.agents/mcp_config.json`; Abstract should integrate only through those supported locations, after checking how its per-chat delivery can be isolated.

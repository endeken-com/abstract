# ABS-185 — Agents and themes as plugins, after Paseo

## Decision

Copy Paseo's two contracts (Apache-2.0, read at
[`getpaseo/paseo@0952ddb`](https://github.com/getpaseo/paseo/tree/0952ddbd4bca85ea0a870256afde97275e59e22b))
onto Abstract's existing plugin host, and change only what Abstract's sandbox and
process model force:

- **Themes** (`contributes.themes`) take Paseo's theme schema verbatim — `id`, `name`,
  `appearance`, eight hex `colors` — plus an optional `tokens` map that overrides any of
  Abstract's own palette roles. A theme is data: no script runs, no capability is asked
  for, and the phone gets it as data. Graphite, Paper and Ink become three bundled theme
  plugins whose manifests hold today's values; Swift keeps only the derivation.
- **Agents** (`contributes.agents`) take Paseo's `ProviderRegistration` shape — `id`,
  `label`, `icon`, a default `command`, `connect` — its catalog (models, modes, thinking
  options), its capability negotiation and its `send` / `onEvent` / `close` connection.
  What changes: **the plugin never spawns anything.** Its agent script returns launch specs
  and stdin lines; the host runs the declared binary through the chat's executor and hands
  the script each output line to turn into Abstract's `AgentEvent`s. The script runs in a
  JavaScriptCore context inside `AbstractCore` with no I/O at all, so it is fast, works
  for `abstract` on the command line and on a paired Mac, and replays a log to the same
  chat everywhere.

**Go**, in the ticket's order: themes first (PR 2), then the agent contribution with
OpenCode and Muse (PR 3), then Claude and Codex, deleting the Swift providers (PR 4).
Agents don't move until the owner approves this note.

Paseo's provider code is unsandboxed Node in a daemon subprocess: it spawns the CLI,
holds the session, and publishes complete timeline snapshots (`timeline.item`, reusing an
`id` to update). The ticket rules that out ("Not this"), and Abstract's own model —
raw lines logged, parsed live and again on replay — needs something else at that seam.

## 1. Themes

### Manifest

```json
"contributes": {
  "themes": [
    {
      "id": "mocha",
      "name": "Catppuccin Mocha",
      "appearance": "dark",
      "colors": {
        "background": "#1e1e2e", "foreground": "#cdd6f4", "raised": "#313244",
        "control": "#45475a", "border": "#45475a", "accent": "#cba6f7",
        "mutedForeground": "#a6adc8", "ring": "#6c7086"
      },
      "tokens": { "syntaxKeyword": "#cba6f7" }
    }
  ]
}
```

**Copied:** the object, its keys, the hex rule (`#rgb`, `#rrggbb`, `#rrggbbaa`), the name
limit, strictness (an unknown key in a theme or in `colors` fails the install), `accent`
falling back to `foreground`, and the full id `<plugin id>/theme/<theme id>`.

**Changed:**
- `name` is a plain string; Abstract's manifests aren't localised.
- `tokens` is new: any `PaletteRole` by name, each a hex colour, each replacing what the
  derivation gave. An unknown role fails the install, like an unknown capability. It is
  how the bundled themes stay pixel-identical, and how a theme fixes one colour without
  forking the derivation.
- At most 8 themes per plugin. No capability: a theme sees nothing and runs nothing. The
  review screen lists them ("Themes — Catppuccin Mocha, in Settings → Appearance").
- Themes resolve from usable plugins only, like every other contribution. Turning the
  plugin off falls back to the default (Graphite), as Paseo does.

### Derivation

One pure function in `AbstractCore`, `ThemeDerivation.palette(for:)`, after Paseo's
`buildDarkPluginTheme` / `buildLightPluginTheme`:

| Abstract role | Dark | Light |
|---|---|---|
| `canvas` | `background` | `background` |
| `code` | `background` 20% toward black | `background` halfway to `raised` |
| `sidebar` | `background` 17% toward black | `raised` |
| `surface` | `raised` | `raised` |
| `surfaceRaised` | `raised` halfway to `control` | `background` |
| `inset` | `control` | `control` |
| `field` | `background` halfway to `raised` | `background` |
| `border` | `border` | `border` |
| `borderStrong`, `fieldBorder` | `border` at 1.6× its opacity (opaque: 15% toward `foreground`) | same |
| `fieldBorderFocused` | `ring` | `ring` |
| `hover`, `selection`, `findMatch` | `foreground` at 5% / 8.5% / 16% | `foreground` at 4% / 6.5% / 11% |
| `text`, `attention`, `accent` | `foreground` (`accent` when given) | same |
| `prose` | `foreground` 8% toward `background` | same |
| `textSecondary` | `mutedForeground` | `mutedForeground` |
| `textTertiary` | `mutedForeground` halfway to `ring` | same |
| `warning` | `mutedForeground` 65% toward `foreground` | same |
| `onAccent` | `background` | `background` |
| diff, pull request, syntax, usage, find, `terminal*` | Graphite's values | Paper's values |

Paseo keeps diff, status and ANSI colours as per-appearance constants rather than
deriving them from eight tokens; Abstract does the same, so a third-party dark theme gets
One Dark syntax and Graphite's diff colours, re-checked for contrast (below). The
terminal's 16 ANSI colours join `PaletteRole` (`terminalBlack` … `terminalBrightWhite`),
so `TerminalTheme`'s own table goes and the terminal follows any theme.

**Bundled themes** are `sh.abstract.theme.graphite`, `.paper` and `.ink`, each a package
with only a manifest, under `Abstract/Resources/Plugins/`, on by default like GitHub. Each sets the eight tokens and
overrides every role whose derived value differs from today's, so a test can assert that
each bundled theme's palette equals today's table, role by role. After that the only
colour values left in Swift are the derivation's per-appearance constants.

### Choosing a theme

- `ThemeChoice` stops being an enum: it is `system` or a full theme id. The stored
  `theme` default keeps its key; `graphite`, `paper` and `ink` read as the bundled ids, so
  nobody's choice changes.
- Settings → Appearance lists every installed theme, bundled first, then by name, each
  with its window preview. **Match System** gets two pickers, a light theme and a dark
  theme (Paper and Graphite by default). With "Increase contrast" on, Match System keeps
  today's rule while the dark pick is the default: Ink in Dark mode, stronger hairlines on
  the light theme.
- `Theme` (the enum) becomes `ResolvedTheme { id, name, appearance, palette }`. Everything
  that switched on `.paper` asks `appearance` instead; `PaletteRole.swatch(in:)` reads the
  palette.
- ⌘K's "Theme: …" commands list every installed theme.

### Plugins follow the theme

`PluginAppearance` carries the `ResolvedTheme`: `--abstract-<role>` is every role of the
derived palette, `data-abstract-theme` is the theme's id, and `colorScheme` its
appearance. The plugin kit (ABS-134) needs no change: it already reads only the tokens.

### The phone

`RemoteSnapshot.theme` (optional, for older peers) carries the Mac's theme as data:
`{ id, name, appearance, tokens: { role: "#rrggbb" | "#rrggbbaa" } }`, the derived
palette, never a script (ABS-84 §6). Under Match System it carries both picks and the
phone chooses by its own appearance. The phone keeps Graphite until a snapshot says
otherwise, and keeps the last theme it saw. Its screens read one `theme.ts` instead of
their own constants.

### Contrast

A derived foreground is lifted toward white on a dark theme, black on a light one, until
it clears 4.5:1 on every opaque surface (text and prose 7:1), which is the bar
`ThemePaletteTests` holds Ink to (ABS-68). A wash text sits on (selection, find, diff)
fades until the text reads on it. A colour given in `tokens` is taken as written. So a sample theme with only
Paseo's eight tokens passes the Ink test, light and dark, and the bundled themes keep
exactly today's values (their low-contrast roles, like Graphite's comments, are written
out). The tests run the Ink checks over the sample theme's derivations and report the
lowest ratio of every bundled theme, as today.

## 2. Agents

### Manifest

```json
"capabilities": ["agents"],
"agent": "agent.js",
"contributes": {
  "agents": [
    {
      "id": "opencode",
      "label": "OpenCode",
      "icon": "icon.svg",
      "command": ["opencode"],
      "install": "brew install sst/tap/opencode",
      "detect": ["--version"]
    }
  ]
}
```

**Copied:** `id`, `label`, `description`, `icon` (a package-relative, self-contained SVG,
checked by Paseo's SVG rules), `command` as the default executable and argument prefix,
and the idea that the host resolves it (the user's binary override, the login PATH) before
the plugin sees it.

**Changed:**
- `command[0]` follows `cli`'s rule: a plain program name, never a shell, an interpreter
  or `git`. The agent may only ever run that binary, with any arguments; nothing else.
- `install` and `detect` replace Paseo's `status()`: Abstract already detects agents by
  running the binary through the executor and shows the install hint.
- `agent` names the agent script (like `background`). It is plain JavaScript loaded into
  a JavaScriptCore context, not a page: no DOM, no `fetch`, no timers, no bridge but
  `AbstractAgent`.
- A new capability, `agents`: "Runs opencode as an agent in your chats". It is the
  highest-trust thing a plugin can be — an agent edits your worktree and runs commands —
  so it is reviewed like `cli`, and an update that changes `command` is reviewed again.
- Agent ids share one namespace; a bundled id wins over a third-party plugin's.

### The script

```js
AbstractAgent.register("opencode", {
  capabilities: ["prompt.image", "session.persistence", "permission", "interrupt"],
  catalog(input) { … },             // → { models, modes, thinkingOptions, defaults }
  launch(ctx) { … },                // → { args, env, stdin, keepStdinOpen, files }
  resume(ctx, sessionId) { … },     // → the same
  connect(session) {                // one per running process
    return {
      send(input) { … },            // → stdin lines: message, permission, interrupt, stop task
      feed(lines) { … },            // → AgentEvent[] for a batch of { line, stream }
      exit(code) { … },             // → AgentEvent[]
      close() {},
    };
  },
});
```

| Paseo | Abstract |
|---|---|
| `connect(request)` with `versions`, `capabilities` | `register` + `negotiate(offered, supported)`, copied; protocol version 1 |
| `send(input)` returns, results are events | `send(input)` returns the stdin lines to write; the host writes them. `session.prompt` (message, images, steer) → `buildUserMessage`; `session.permission` → `buildPermissionResponse`; `session.interrupt` → `buildInterrupt`; plus `stopTask`, `background`, `setMode` for what Claude does today |
| `onEvent(listener)`: `timeline.item` snapshots, `session.turn`, `session.usage`, `session.permission`… | `feed(lines)` returns `AgentEvent`s in a JSON form (`{ type: "text", role, text, blockId, partial }`, `toolUse` with an `edit` preview, `toolResult`, `usage`, `sessionId`, `turnEnd`, `permissionRequest`, `notice`, `task`, `subagent`, `compaction`, `error`) that decode 1:1 into today's enum |
| `close()` | `close()`; the host ends the process |
| `request.launch` + `spawnProcess` | `launch(ctx)` returns args and env for the declared binary; the host spawns it through the chat's executor, so paired Macs, the git budget (ABS-45), per-chat MCP and skills config (ABS-122/123) and `abstract`'s headless host keep working |
| `catalog` input | `catalog({ discovered })`: static choices, plus the output of an optional `discover` command the host runs through the executor (`opencode models`, Codex's model list) |
| `session.opened.persistence` | the `sessionId` event, stored as today; `resume(ctx, sessionId)` |
| `session.configure` settings | not now: Abstract's composer offers model, effort and permission mode, which the catalog fills |
| ACP shim (`runAcpProvider`) | not now; a follow-up can ship it as a JS library an agent script includes |

**Why events and not Paseo's timeline snapshots.** Abstract logs each raw line and folds
the log again on relaunch, on another Mac and in history search; `feed` has to be a pure
function of the lines it was given, which `OutputParser` already is. Keeping `AgentEvent`
keeps the transcript, tool rows, edit previews, usage, permissions and stop exactly as they
are, and lets today's fixture tests prove it: the same fixture through the Swift parser
and through the plugin must give the same events.

**What else the host offers the script**, each scoped to the chat and synchronous on the
reader queue as today:
- `ctx.worktree.read(path)` and `ctx.worktree.committed(path)`, for Codex's edit diffs
  (today's `CodexEditDiffs` enricher), inside the chat's worktree only;
- `ctx.files`: files the launch asks for in the chat's own config folder (Claude's MCP
  config, OpenCode's instructions), never elsewhere;
- side-channel runs for compaction and naming: the script returns a launch and folds that
  process's lines, as `Compactor` and `namingLaunch` do today.

Skills delivery (`addedDirectory`, `codexHome`, `skillsPath`) and MCP access
(`none`, `allowOrOff`, `askFirst`) stay host logic; the agent declares which it takes.

### Capabilities → "this agent can't…"

Negotiated like Paseo's, and each replaces one optional `ProviderDefinition` member, so
ABS-23's notices read them instead of the type: `prompt.message` (required),
`prompt.image`, `prompt.steer` (stdin follow-ups), `interrupt`, `permission`,
`permission.mode` (switch mode live), `session.persistence` (resume), `task.stop`,
`task.background`, `mcp` (with its access level), `skills`, `compaction`, `naming`.

### Speed

`JSContext` runs in-process, so a line costs one call, not an IPC round trip to a web
view. Lines are handed over in batches — everything the reader has (up to 256 lines) live,
and the whole log on replay — and events come back as one array. PR 3 adds a benchmark
that replays every fixture through the Swift parser and through the plugin; the plugin
must stay within 3× of Swift and under 1 ms per 100 lines on CI. Each running chat gets its
own context, so a slow parse holds up only its chat.

### Bundled agents and the registry

`sh.abstract.agent.claude`, `.codex`, `.opencode` and `.muse`, each a package with a
manifest, `agent.js` and `icon.svg`, contributing the agent ids chats already store
(`claude`, `codex`, `opencode`, `muse`), so no chat, profile or automation moves.
`ProviderRegistry` becomes the registry of installed agent plugins: `all` is whatever
usable plugins contribute, `makeParser(id)` returns a parser backed by the plugin's
context, and `name(id)` reads its label. Retired agents keep reading through Codex's plugin.
"One type per agent" becomes "one plugin per agent".

### The phone

No plugin code runs on the phone, so it can't fold a third-party agent's lines. The Mac
already parses every line; with PR 3 the remote `lines` event also carries the events each
line folded to, and the phone renders those when present, keeping its own fold for older
Macs. Agent labels and icons reach the phone in the snapshot, as data.

### Deleted at the end (PR 4)

`ClaudeProvider`, `CodexProvider`, `OpenCodeProvider`, `MuseProvider`, their compactors
and model helpers, and the four agent names in `ProviderRegistry.swift`. The
`usageClaude` … `usageMuse` roles become series colours an agent contribution can pick.

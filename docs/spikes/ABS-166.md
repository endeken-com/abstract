# ABS-166 — Automations that are pleasant and easy to create, run and follow

## Decision

Keep the shape that works — one list, one document page per automation, sentence
chips for schedules, explicit Save — and fix the three things that make it hard
today: the list does not say how the last run went, the setup page packs six
decisions into one prose sentence with advanced choices at the same level as
basic ones, and run outcomes use words nobody can decode without opening the
chat. The redesign is presentation only. The engine, RRULE storage, models and
scheduling semantics in
[Records.swift](../../Packages/AbstractCore/Sources/AbstractCore/Models/Records.swift#L314)
do not change, and every existing automation — including the Linear dispatcher
under `~/.abstract/automations/` — keeps running untouched.

One new pure view-state in `AbstractCore` carries every new word:
`RunOutcome` (a run plus its chat status, reduced to one word and tint) and
`AutomationSummary` (the read-back line: schedule, next run, last run). Views
render it; nothing else decides wording. The build ticket is **M**.

## What is confusing today (audit)

- The list row shows name, schedule and next run only
  ([AutomationsView.swift](../../Abstract/Features/Automations/AutomationsView.swift#L191)).
  Last run, failure and "needs you" are invisible until you open the page and
  its Run history tab. On/off is a bare diamond with no control; there is no
  Run now or Pause without opening the page. Three filters (project, agent,
  state) sit on the list even when there are two automations.
- The setup page orders §When it runs first and the instructions — the main
  content — last
  ([AutomationEditor.swift](../../Abstract/Features/Automations/AutomationEditor.swift#L242)).
  Still-going, missed-runs and only-when-changed sentences are always expanded.
  Where a run happens is one wrapping sentence holding chat mode, project, Mac,
  profile/workflow, agent/model/effort and permissions
  ([ScopeSentence](../../Abstract/Features/Automations/AutomationEditor.swift#L646)),
  with up to six detached notes piled underneath. It reads nicely and scans badly.
- Save problems show as small text at the top right, far from the field at fault
  ([saveControls](../../Abstract/Features/Automations/AutomationsView.swift#L407),
  [blocker](../../Abstract/Features/Automations/AutomationEditor.swift#L230)).
  The Active switch saves instantly while everything else needs Save, and
  Run now silently runs the saved version when there are unsaved edits (a
  tooltip is the only hint).
- Creating shows the "Describe it" AI box and the full blank editor at once:
  two competing starts, no examples. The empty-state paragraph tries to explain
  pinned chats and worker chats in one breath.
- Run history's outcome is the raw chat status ("Your turn", "Created")
  ([AutomationRunHistory.swift](../../Abstract/Features/Automations/AutomationRunHistory.swift#L117)),
  failed errors render in raw mono, the 50-run cap is silent, and the footer
  ("A run counts as started once…") explains a subtlety nobody asked about.
- Real usage (the Linear dispatcher) is a pinned automation whose long
  instructions point at an external rules file, which starts worker chats and
  keeps its own state file. What its owner needs at a glance is: did the last
  run finish or does it need me, when is the next one, and one click into its
  chat. Today that takes three clicks and reading a tab. Long instructions also
  matter: they must not sit below schedules and scope.

## The list

Keep grouping by project, the heading count, and the stored filters, but show
the filter bar only when a filter is on or there are more than 8 automations;
otherwise a quiet **Filter** button opens the same three menus. Each row
becomes two lines and answers the dispatcher questions without a click:

```
 ◆ Nightly dependency bump                     Next tomorrow, 09:00
   Every day at 09:00 · Abstract · Claude      ● Done · 2h ago
 ◇ Issue triage                                          Paused
   Every weekday at 08:30 · payments-api       ● No runs yet
 ◆ Linear dispatcher                          Next today, 19:00
   Every day at 03:30 and 19:00 · in "Dispatcher"  ● Needs you
```

- Line 1: state diamond (solid = active, outline = paused, as today), name,
  and on the right `Next <moment>` — or **Paused**, **Runs by hand only**,
  **Runs on events**, **No more runs** for the other `AutomationText.next`
  cases ([AutomationSupport.swift](../../Abstract/Features/Automations/AutomationSupport.swift#L254)).
- Line 2: schedule in words (existing `AutomationText.schedule`), then chat
  (`in "…"`), Mac and agent name when they add information; on the right the
  latest run's `RunOutcome` word with its dot: **Needs you**, **Failed**,
  **Working**, **Done · 2h ago**, **Skipped**, **No runs yet**.
- When any latest outcome is Needs you or Failed, one line under the heading
  counts them: "2 need you · 1 failed". It is text, not a new filter.
- Paused rows render name and schedule in tertiary ink.
- Hover (and right-click / keyboard focus) on a row offers **Run now** and
  **Pause**/**Resume**; the context menu adds **Open last chat** (when the
  latest run has one) and **Duplicate**. Row click still opens the page.
- `AppModel` gains the latest run per automation, refreshed wherever runs are
  loaded today, so the list never queries per row.

## The automation page

The header keeps title, Active switch and Save/Discard, and gains the
read-back line under the switch — the whole automation in one breath, from the
saved version:

```
 Every weekday at 09:00 · Next tomorrow, 09:00 · Last run Done, 2h ago   Open chat
```

(`Open chat` appears when the latest run, or the continued chat, exists. For a
new automation the line is absent.) The switch gets its state in words next to
it — **Active** / **Paused** — and one caption when the automation exists:
"Takes effect now, even before you save other changes." Tabs are renamed
**Setup** and **Runs**.

Run now with unsaved edits no longer guesses: it asks with three buttons —
**Save and Run**, **Run Saved Version**, **Cancel**. Save problems move to the
field at fault: empty instructions get a caption under the Instructions
heading, a bad schedule keeps today's inline message, and the two cross-field
blockers (workflow + other Mac + continued chat; events + other Mac) show as a
caption under the row they name. The header keeps only the first blocker's
short text next to a disabled Save, as today.

### Setup tab: three labelled sections

```
 WHAT IT DOES
 Instructions                                          Edit
 <rendered Markdown…>

 WHEN IT RUNS
 🕘 Every weekday ▾ at 09:00 ▾  · Next run tomorrow, 09:00      ×
 ＋ Add schedule
 ⚡ When a chat is archived ▾                                    ×
 ＋ Add an event…
 ▸ More run options — skip if still running · run missed runs once

 WHERE IT RUNS
 Chat          Same chat every run ▾
 Project       Abstract ▾
 Mac           This Mac ▾
 Profile       No profile ▾
 Agent         Claude · Opus · High ▾
 Permissions   Edits accepted ▾
```

1. **What it does** — instructions first (the title already carries the name).
   Edit/read toggle and Markdown editor unchanged; the placeholder gains a
   shape to copy: what to do, in what order, what to report back.
2. **When it runs** — today's schedule rows, preset chips, time picker and
   inline errors unchanged, with **Trigger** renamed **Schedule** everywhere
   a user reads it (add/remove/help text; code names stay). Custom stays in the
   preset menu as **Custom rule (advanced)**. Events follow under the same
   section with today's rows. The still-going, missed-runs and
   only-when-changed sentences move into a **More run options** disclosure,
   collapsed by default; its closed label summarises any non-default choice
   ("— skip if still running"), and shows nothing extra at defaults.
3. **Where it runs** — the scope sentence becomes labelled rows: a 110 pt
   label column, then the exact chips and menus that exist today (chat,
   project, Mac, profile/workflow, agent, permissions), each row shown under
   the same conditions the sentence fragments are shown today. Every note and
   warning moves under its own row: missing agent under Agent, offline or
   project-less Mac under Mac, broken workflow under Profile, "nobody is there
   to answer" under Permissions, continued-chat notes under Chat. Chat choices
   are renamed: **New chat each run**, **Same chat every run** ("First run
   creates it; later runs continue it"), then specific chats as today.

### Creating

One start, not two. The new page opens on the Describe box (focused, as today)
with three example chips under it that fill the box — "Every weekday at 9,
triage new issues and tell me what needs me", "Nightly, update dependencies
and fix what breaks", "Every Monday, summarise last week's merged work" — and
a quiet **Start blank instead** button that hides the box and focuses the
title. The setup sections sit below, pre-filled with today's defaults (daily
09:00, first project, first installed agent, edits accepted, new chat each
run). After a successful draft the box collapses to one line, "Drafted — check
the setup below", with **Draft again** to reopen it. These examples are text
for the drafting prompt, not stored templates; no template storage is added.
The empty state shortens to: "Run an agent on a schedule, or when something
happens in a chat. Each run is a chat you can read and reply to." One button:
**New Automation**.

## Runs tab

```
 ● Needs you    On schedule              Open chat
   Today, 09:00 · "Nightly dependency bump"
 ● Done         Run by hand              Open chat
   Yesterday, 09:00 · "Nightly dependency bump"
 ● Failed       On schedule
   Mon, Oct 19, 09:00
   git worktree add: '…' is already checked out
 ● Skipped      On schedule
   Sun, Oct 18, 09:00
   The project hadn't changed since the last run.
```

One mapping decides every outcome — `RunOutcome(run, sessionStatus)`:

| Run | Chat | Word |
|---|---|---|
| creating | — | Starting… |
| failed | — | Failed (+ error, body text, selectable) |
| skipped | — | Skipped (+ reason) |
| created | waitingInput | Needs you |
| created | running / provisioning | Working |
| created | idle / finished | Done |
| created | errored | Failed |
| created | created | Ready |
| created | chat deleted | Chat deleted |

Needs you and Failed use the attention/removed tints the app already uses for
those chat states
([Status.swift](../../Abstract/Components/Status.swift#L4)); the rest stay
secondary ink, always a dot plus a word. Trigger words become **On schedule**,
**Run by hand**, or the event phrase that already exists ("'Fix login' was
archived"). The whole row still opens the chat, and gains an explicit
**Open chat** button so that is discoverable. The caveat footer goes; when 50
runs are shown the footer reads "Showing the latest 50 runs." Empty states
keep today's wording, which is already plain.

## Words (complete list of renames)

Settings → **Setup** · Run history → **Runs** · Trigger → **Schedule** (UI
only) · Add trigger → **Add schedule** · Custom rule → **Custom rule
(advanced)** · Starts a new chat → **New chat each run** · Continues a chat of
its own → **Same chat every run** · Scheduled → **On schedule** · Manual →
**Run by hand** · Manual only → **Runs by hand only** · On events → **Runs on
events** · No upcoming runs → **No more runs**. Everything else — **Run now**,
**Save**, **Discard**, **Active**, **Paused**, preset phrases, permission
phrases, event phrases — keeps today's words.

## What does not change

Engine and scheduler; RRULE format, time zones, `nextRunAt`; the `Automation`,
`AutomationTrigger` and `AutomationRun` models and their store tables; events,
concurrency, missed-runs and only-when-changed semantics and defaults; Mac,
profile and workflow resolution at run time; Draft with AI and its proposal
shape; the explicit Save/Discard model and leave-confirmation; duplicate and
delete; the `~/.abstract/automations/` files (they are a run's own working
files, never read by this UI). No migration, no version change.

## Implementation and test seams

- `AbstractCore`: new `Automations/AutomationPresentation.swift` with
  `RunOutcome` (run + optional `SessionStatus` → word, needsAttention flag)
  and `AutomationSummary` (automation + latest run + now → the list line-2 and
  header strings). Pure, like
  [AutomationListing](../../Packages/AbstractCore/Sources/AbstractCore/Automations/AutomationListing.swift),
  so every word above is unit-tested without SwiftUI.
- Store: one batch `latestRuns() -> [String: AutomationRun]` next to the
  existing `runs(automationId:limit:)`; `AppModel` holds it beside
  `automations` and refreshes it in `reload()` and after `runAutomationNow`.
- App: restructure only the three Automations files — list rows and header
  summary in `AutomationsView.swift`, section order/labelled rows/disclosure
  in `AutomationEditor.swift` (chips, menus, `TriggerDraft`, blockers reused
  as-is), outcome rows in `AutomationRunHistory.swift`. Demo data gains a
  needs-you run and a skipped run so screenshots cover them
  ([DemoBootstrap.swift](../../Abstract/Demo/DemoBootstrap.swift#L92)).
- Tests: `RunOutcome` for every row of the table; summary strings for paused,
  by-hand, on-events, finished-schedule and no-runs automations; `latestRuns`
  batch picks the newest per automation; existing automation, scheduling,
  listing and drafting tests pass unchanged. Screenshots before/after, light
  and dark: list, setup, runs, new automation.

**Size for ABS-161: M.** No model, schema or engine change, but three view
files are restructured, one Core presentation type and one store query are
new, and the screenshot pass covers four screens in two appearances. **Go** —
no open UX choice remains; the build ticket implements exactly this note.
